## 1. 本番運用設計

| 領域 | 設計 |
|---|---|
| **観測性** | Workers Analytics Engine（リクエスト/エージェント実行メトリクス）+ Sentry（例外トラッキング）+ 構造化ログ（`agent_runs`テーブルへの記録と二重化） |
| **アラート** | エラー率・動画生成失敗率・送信バウンス率が閾値超過でSlack/PagerDuty通知 |
| **デプロイ** | GitHub Actions → `wrangler deploy` に Gradual Deployments（Cloudflareのバージョン間トラフィック分割）を使い、新バージョンを10%→50%→100%と段階的に展開 |
| **冪等性** | Stripe Webhook・請求処理・メール送信キューはすべて冪等キー必須（`idempotency_key`列）。リトライされても二重課金・二重送信が起きない設計 |
| **サーキットブレーカー** | 動画生成プロバイダAPIの障害時、`motion-generator-mcp`内で自動的に別プロバイダへフェイルオーバー、または`qualityTier: draft`にフォールバック |
| **バックアップ/DR** | Supabase Point-in-Time Recovery、R2は複数リージョンレプリケーション設定を検討 |
| **ヘルスチェック** | 各Worker/MCPサーバーに`/health`エンドポイント、外形監視 |

## 2. セキュリティ設計

- **テナント分離**：Postgres RLS（§02参照）を第一防衛線とし、Worker側でも`tenant_id`をJWTから強制的に注入（クライアント入力の`tenant_id`は信用しない）
- **認証・認可**：Clerk Organizations + RBAC（owner/admin/member/viewer）。請求・契約系操作はowner/adminのみ
- **シークレット管理**：Cloudflare Workers Secretsで管理、コードに一切ベイクしない。テナントごとのGmail/Slack OAuthトークンは`integration_credentials`テーブルにアプリケーションレベルで暗号化して格納
- **レート制限**：Workers KVベースのスライディングウィンドウ、プラン別上限（§コスト最適化とも連動）
- **監査ログ**：請求・契約・送信承認など重要操作は`audit_log`テーブルに不可変記録
- **Webhook検証**：Stripe/Gmail Push通知等はすべて署名検証必須
- **PIIの取り扱い**：リード（企業担当者の個人情報）は目的外利用の禁止、保持期間ポリシー（例：180日で自動匿名化）、削除リクエスト対応フローを用意

## 3. コンプライアンス設計（Lead Finder / AI Sales Agent）

ご依頼原文末尾の「各サービスの利用規約・適用法令・プライバシー要件を満たす設計とし、必要に応じて利用者の明示的な確認や承認フローを組み込む」を具体化した設計です。ここは本プロダクトの事業継続性に直結するため、他の項目と同じ重みで詳細化しています。なお、以下は一般的なアーキテクチャ上の指針であり法的助言ではありません。実運用前に各国・各サービスの最新規約と、対象国の弁護士による確認を推奨します。

### 3.1 データソースの階層化

| ティア | ソース | 方針 |
|---|---|---|
| **Tier 1（推奨・既定）** | Google Places API, Crunchbase API, Product Hunt API, YouTube Data API, Shopify App Store公式連携 | 公式APIのみを`lead-enrichment-mcp`のデフォルトアダプタとして実装 |
| **Tier 1相当（ライセンス品）** | Apollo.io / Clearbit / People Data Labs等の法人向けデータプロバイダ | 自前スクレイピングを避け、データ取得の合法性を担保済みの事業者を使う。**「ゼロから作らず実績あるものを使う」方針とも合致**します |
| **Tier 2（低リスク）** | リード企業自身の公式サイト（`自社サイト`） | 一般公開されたマーケティングサイトの閲覧は、過度な高頻度アクセスを避ける限り比較的低リスク。Browser Runでの取得も可 |
| **Tier 3（非推奨・未実装）** | LinkedIn / Instagram / X の直接スクレイピング | これらのToSは自動収集を明確に禁止しており、実際に法的紛争に発展した事例もあります（例：hiQ Labs v. LinkedIn）。アカウント停止・訴訟リスクがあるため、**本設計では実装しません**。代替として、LinkedIn Sales Navigator等の公式パートナーAPI、または各社が許諾したデータプロバイダ経由での取得を推奨します |

`leads`テーブルの`source_provider`・`legal_basis`列（§02）は、この階層のどこから来たデータかを常に追跡可能にするためのものです。

### 3.2 アウトリーチのコンプライアンスモジュール

`communication-mcp`の`send_email`等は、内部で以下を**強制的に**通過させます（バイパス不可）。

1. `suppression_list`照合（オプトアウト済み・バウンス済みは即ブロック）
2. `consent_status`と管轄地域の突合（下表）
3. 送信頻度・ウォームアップ制限のチェック
4. 配信停止リンクの自動挿入、送信者情報の明記

| 地域/法令 | 基本モデル | 実装上の対応 |
|---|---|---|
| 米国 CAN-SPAM | オプトアウト方式（事前同意不要だが表示義務あり） | 正確なヘッダー、物理住所表記、配信停止リンク必須 |
| EU GDPR / ePrivacy | 原則オプトイン、B2Bの正当な利益に基づく例外は限定的 | 初回連絡は最小限のデータ利用に留め、容易な拒否手段を提供。不明な場合はオプトイン優先 |
| 日本 特定電子メール法 | 原則オプトイン（事前同意が必要） | 日本国内の連絡先には、既存取引関係がある場合を除き自動送信を既定でオフにし、同意取得フローを別途要求 |

Sales Agentの送信キャンペーンには`jurisdiction`フィールドを持たせ、地域ごとに異なるデフォルト（例：JP宛は`requires_opt_in: true`）を適用します。

### 3.3 SNS DM送信について

Instagram/LinkedIn/X等は、営業目的の自動DM送信を許可する公式APIをほぼ提供していません（提供されていても限定的・審査制）。非公式な自動化はアカウント凍結リスクが高いため、本設計では**Email（Gmail API/Outlook）を自動化の主軸**とし、SNS DMは「AIが下書きを作成し、担当者が手動で送る」半自動運用を既定にすることを推奨します。Slack/Discordは、相手が既にワークスペースに参加している既存見込み客とのフォローアップ用途に限定するのが安全です。

### 3.4 送信インフラに関する実務上の注意

個人のGmail/Outlookアカウント経由で数千〜数万通を送ると、即座にスパム判定・アカウント制限を受けます。実際に「Gmail API連携」が有効なのは、**テナント自身の既存顧客への少量フォローアップ**（数十〜数百通/日）に限定し、コールドアウトリーチの本体は、専用のトランザクショナル/マーケティングメール基盤（Resend, Postmark, Amazon SESなど）＋ドメインウォームアップ＋SPF/DKIM/DMARC設定を前提とした別経路として設計することを強く推奨します。

## 4. コスト最適化

動画生成AI APIの利用料が、本プロダクトの変動費の大部分を占める見込みです。以下のレバーで最適化します。

1. **二段階レンダリング**：まず低コスト/低解像度の`draft`で複数案を生成しテナントに選ばせ、確定案のみ高コストの`final`でレンダリング（§02の`qualityTier`）
2. **プロバイダのコストベースルーティング**：`motion-generator-mcp`が用途（下書き/最終/リード向けパーソナライズ）に応じ最安のプロバイダへ自動振り分け
3. **モデルの使い分け**：QAの一次スクリーニングやタグ付けのような軽量タスクはWorkers AIの安価なモデルに、クリエイティブディレクションのような高度な判断はClaude/GPT-4クラスに、と役割ごとにモデルコストを最適化
4. **ストレージ**：R2は転送量（egress）が無料のため、動画配信量が多いこのプロダクトでは特に有利です（保存は$0.015/GB、書き込み系操作が$4.50/百万回、読み取り系が$0.36/百万回という料金体系で、S3のような配信量課金が発生しません）。ポートフォリオサイトからの動画再生・DL提案時のコストを大きく抑制できます
5. **Workersのリクエスト課金モデル**：常時起動するNode.jsサーバーと異なり、リクエスト単位課金・アイドル時無料のため、テナント数が少ない立ち上げ期のインフラ費用を最小化できます
6. **キャッシュ**：同一商品×同一プロンプト仕様の再生成要求はWorkers KVでキャッシュし、無駄な再生成コールを防止
7. **バッチ処理**：一括エンリッチメント等はQueuesでオフピーク時間帯に平準化
